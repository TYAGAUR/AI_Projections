# Day 18: Finding information by meaning

This guide explains `note18` in beginner-friendly language. The lesson builds a small knowledge search feature using text embeddings, OpenAI, and ChromaDB.

## What you build

By the end, your app can:

1. Turn text into numbers that represent its meaning.
2. Save those numbers and the original text in a vector database.
3. Turn a question into numbers too.
4. Find saved text with a similar meaning, even if it uses different words.

This is the **retrieval** part of Retrieval-Augmented Generation (RAG). This lesson finds relevant information, but does not yet send it to an LLM to write an answer.

## Embeddings: meaning represented as numbers

An **embedding** is a list of numbers made by an AI model from text. You can think of it like placing a sentence at a location on a huge map of meaning.

Sentences about similar topics should end up near each other on that map. For example, “I want to learn artificial intelligence” and “I am interested in machine learning” are related, even though they do not use exactly the same words.

The embedding model used in this lesson is OpenAI's `text-embedding-3-small`. It turns text into a vector (a list of numbers). The example vectors in the lesson are just illustrations; real vectors are generated by the model.

## Semantic search and similarity

Traditional keyword search looks for the same words. **Semantic search** looks for similar meaning.

To search:

1. Convert each document into an embedding.
2. Save its embedding, original text, and useful details.
3. Convert the user's question into an embedding.
4. Find the saved vectors closest to the question's vector.
5. Return the matching text and its details.

The lesson introduces **cosine similarity**, a way to compare the direction of two vectors. A higher similarity can suggest that two pieces of text are related, but a score is not a guaranteed relevance percentage. Results depend on the embedding model and the information being searched.

## ChromaDB: a database for vectors

ChromaDB stores embeddings alongside their original text and **metadata**, such as a title or user ID. Its collection is a little like a table designed for vector search.

The lesson configures a local persistent ChromaDB collection in the `chroma_db` folder. This lets the data remain after the app restarts on your computer. Add `chroma_db/` to `.gitignore` so local database files are not pushed to GitHub. A deployed app also needs persistent storage or a managed vector database.

## The service and API routes

The lesson creates two main service functions:

- `add_knowledge(...)` creates an embedding and stores it with the document and metadata.
- `search_knowledge(...)` creates an embedding for a question and retrieves the closest saved documents.

It also adds two authenticated API routes:

| Route | What it does |
| --- | --- |
| `POST /knowledge/documents` | Adds a title and text to the knowledge collection |
| `POST /knowledge/search` | Searches saved text using a question and `top_k` |

`top_k` means how many matching results to return. The lesson allows values from 1 to 10.

Both routes use the logged-in user's ID. The search filters on that ID so one user does not receive another user's documents. This is a useful starting safeguard, but a real multi-user system still needs careful access-control and tenant-isolation testing.

## Try it in Swagger

Install NumPy and ChromaDB as described in the lesson, then start the app from the project folder:

```powershell
fastapi dev main.py
```

Open `http://127.0.0.1:8000/docs` and authenticate using your existing login flow.

1. Use `POST /knowledge/documents` to add a few short documents, such as one about FastAPI and another about RAG.
2. Use `POST /knowledge/search` with a question phrased differently from the saved text.
3. Check whether the expected document appears among the results.
4. Restart the app and search again to confirm the local ChromaDB data persisted.
5. If you have another test user, verify that they cannot retrieve the first user's documents.

For example, after saving a document about FastAPI, search for “How can I build a Python API?” The search can find it even if those exact words do not appear in the document.

## What this lesson does not do yet

This is a first retrieval demo, not a complete document-search product:

- It stores one full text per record; large documents should be split into smaller, meaningful **chunks**.
- It retrieves relevant text but does not yet send that text to an LLM to generate a grounded answer.
- Adding the same document again creates another record; duplicate detection and document updates are not included.
- A score such as `1 - distance` is a convenient display value, not proof that a result is correct.
- Local storage needs extra setup before deployment to a cloud host.

These are important next steps before using the feature in production.

## Key words to remember

- **Vector**: a list of numbers.
- **Embedding**: a vector representing text's meaning.
- **Metadata**: extra information stored with a document, such as its title or owner.
- **Semantic search**: finding text by meaning rather than exact word matches.
- **Vector database**: a database built to store and search embeddings.
- **RAG**: retrieving helpful information and later giving it to an LLM to help answer a question.
